# 후기 데이터 수집 설계 (익명 집계)

## 현재 상태

**서버 저장소는 구현하지 않았어요.** 지금 앱은 착용 기록을 이 브라우저(localStorage)에만 저장하고, 익명 통계 기여에 동의해도 서버로 전송하지 않아요. 동의하면 익명 레코드가 브라우저의 전송 대기열(`fitcheck.contribQueue.v1`)에만 쌓이고, 화면에도 "준비 중, 서버로 전송되지 않음"이라고 보여줘요. 이 문서의 서버 부분(엔드포인트, 집계, 삭제)은 모두 설계 초안이에요.

> 이 문서는 법률 자문이 아니에요. 개인정보 보호법 등 적용 여부, 동의 문구와 보관 기간은 실제 서비스 전에 **법무 확인이 필요해요.**

## 목표와 비목표

목표
- 사용자가 직접 남긴 착용 기록(작았음·딱 맞음·컸음, 반품 여부)을 **옵트인(선택 동의)** 으로 익명 집계해, 추천의 근거 표본을 쌓아요.
- 집계 결과를 추천 신뢰도(표본 수), 반품 절감 대시보드, 공유 링크, 크롬 확장이 같은 스키마로 쓰게 해요.

비목표
- 쇼핑몰 리뷰를 대량으로 긁어오지 않아요(크롤링 안 함).
- 닉네임, 이름, 연락처, 계정 ID 등 개인을 알아볼 수 있는 정보를 받지 않아요.
- 동의 없이는 아무것도 저장하거나 보내지 않아요.

## 수집 항목

| 필드 | 목적 | 민감도 | 비고 |
| --- | --- | --- | --- |
| `schemaVersion` | 스키마 변경 대응 | 낮음 | 현재 1 |
| `month` | 시기 변화(시즌, 상품 개편) 파악 | 낮음 | `YYYY-MM`, 일·시각은 버림 |
| `domain` | 쇼핑몰별 사이즈 경향 | 낮음 | 호스트 이름만. 경로·쿼리 제외 |
| `category` | 상의·하의 등 종류별 집계 | 낮음 | |
| `size` | 산 사이즈 | 낮음 | |
| `result` | 작음/맞음/큼 | 낮음 | 핵심 라벨 |
| `returned` | 반품 절감 집계 | 낮음 | |
| `parts` | 부위별 여유 | 중간 | 2cm 단위 반올림 |
| `body.gender` | 비슷한 체형 묶음 | 중간 | |
| `body.heightBand` | 비슷한 체형 묶음 | 중간 | 5cm 구간(예: 170-174) |
| `body.weightBand` | 비슷한 체형 묶음 | 중간 | 5kg 구간(예: 60-64) |
| `body.shape` | 체형 묶음 | 중간 | 어깨·배·하체 선택값 |
| `body.preferredFit` | 선호 핏 | 낮음 | |

## 받지 않는 것

상품명, 상품 URL 원문, 사진, 정확한 키·몸무게, 직접 입력한 치수, 평소 사이즈, 기록 시각(초 단위), IP 기반 식별자 저장(서버 구현 시에도 레코드에 붙이지 않음).

상품 식별: 지금은 `domain`만 보내요. 상품별 집계가 필요하면 URL에서 쇼핑몰 상품 번호를 뽑아 `domain + 정규화 상품 ID`로 쓰는 방안이 있지만, 상품 번호가 희소하면 재식별 위험이 커지고 파싱 규칙은 쇼핑몰마다 달라서 아직 구현하지 않았어요.

## k-익명성 기반 공개

- 같은 `(category, domain, 정규화 상품 ID, 성별, heightBand, weightBand)` 묶음에 레코드가 **k개 이상**일 때만 집계를 공개해요.
- k 값은 제안일 뿐이에요. 시작값으로 20을 제안하지만 근거가 되는 측정은 아직 없고, 법무·데이터 담당자와 정해야 해요.
- k 미만 묶음은 더 거친 묶음(구간 넓히기, 상품 ID 빼기)으로 합치고, 그래도 부족하면 공개하지 않아요.
- 응답에는 항상 표본 수 `n`을 같이 내려요.

## 동의 철회와 삭제의 한계

- 철회: 체크를 풀면 브라우저의 전송 대기열이 즉시 지워져요(구현됨).
- 서버로 이미 전송된 뒤에는 레코드에 사용자 식별자가 없어서 **어느 것이 내 기록인지 찾아 지울 수 없어요.** 이건 익명 설계의 대가이고, 동의 문구에도 그대로 적었어요.
- 이미 만들어진 집계 통계에서 개별 기록을 빼는 것도 어려울 수 있어요. 이 한계가 법적으로 허용되는지는 법무 확인이 필요해요.
- 대안(미결정): 기기에만 있는 무작위 기여 토큰을 레코드에 붙이면 삭제 요청이 가능하지만, 같은 사람의 기록을 연결할 수 있게 돼 익명성이 약해져요. 둘 중 무엇을 택할지는 정책 결정이 필요해요.

## 서버 엔드포인트 초안 (미구현)

```
POST /api/feedback-contribution
Content-Type: application/json
{ "records": [ <Contribution>, ... ] }   // 한 번에 최대 50건
→ 202 { "accepted": n }
```

- 같은 출처 검사와 Content-Type 검사는 기존 `/api/*` POST 규칙(`checkPostRequest`)을 재사용해요.
- 서버는 스키마 검증(알 수 없는 필드 거부, 값 범위·열거형 확인)을 하고, 검증을 통과한 필드만 저장해요. 요청 로그에 IP를 남기지 않거나 짧게만 보관해요.
- 집계 조회 초안: `GET /api/fit-stats?domain=&category=&size=` → `{ n, smallRate, trueRate, largeRate, returnRate }` (n이 k 미만이면 `n`만 반환).

## 스키마와 확장 규칙

예시 (`src/lib/contribution.js`의 `toContribution`이 만드는 값):

```json
{
  "schemaVersion": 1,
  "month": "2026-11",
  "domain": "musinsa.com",
  "category": "top",
  "size": "M",
  "result": "large",
  "returned": true,
  "parts": { "chest": 10, "shoulder": 2 },
  "body": {
    "gender": "male",
    "heightBand": "170-174",
    "weightBand": "60-64",
    "shape": { "shoulder": "normal", "belly": "none", "lower": "normal" },
    "preferredFit": "regular"
  }
}
```

- 필드 추가는 하위 호환(선택 필드)으로 하고 `schemaVersion`을 올려요. 필드 삭제·의미 변경은 새 버전으로 만들어요.
- 수집 항목을 늘리면 동의 문구도 바뀌므로 `CONSENT_VERSION`을 올려, 이전 동의가 자동으로 무효가 되게 했어요(`src/data/consent.js`).
- 기존 기록(`fitcheck.feedback.v1`)의 형식과 키는 바꾸지 않았어요. 동의 상태(`fitcheck.consent.v1`)와 대기열은 별도 키예요.

## 로드맵 연계

| 로드맵 | 이 스키마에서 쓰는 방식 |
| --- | --- |
| 추천 신뢰도 표시 | 비슷한 체형 묶음의 `n`과 `result` 분포로 "기록 n건 기준" 표시 |
| 반품 절감 대시보드(B2B) | `domain`·`category`·`size`별 `returned` 비율. k 미만이면 비공개 |
| 공유 링크 | 개인정보 없는 요약만 담기(상품, 추천 사이즈, 체형 구간). 정확한 키·몸무게는 넣지 않음 |
| 크롬 확장 | 같은 `toContribution`과 동의 문구를 재사용. 확장은 별도 저장소를 쓰므로 동의도 확장에서 따로 받아야 함 |

## 동의 문구 (사용자에게 보이는 내용)

체크박스: **익명 통계로 보내기 (선택)** (기본 해제)

- 보내는 항목: 성별, 키(5cm 구간), 몸무게(5kg 구간), 체형 선택값, 선호 핏, 옷 종류, 산 사이즈, 착용감, 반품 여부, 부위별 여유(2cm 단위), 상품 사이트 도메인, 기록한 달(연-월).
- 보내지 않는 항목: 이름·닉네임·연락처, 정확한 키·몸무게, 사진, 상품명, 상품 주소(URL) 전체.
- 목적: 비슷한 체형의 착용 결과를 익명으로 모아 추천 근거(표본 수)와 반품 감소 통계를 만드는 데만 써요.
- 익명 처리: 일정 인원 이상이 모인 묶음만 통계로 공개해요. 한 사람을 가려낼 수 있는 값은 보내지 않아요.
- 철회: 체크를 풀면 이 브라우저에 쌓인 전송 대기 기록이 바로 지워져요. 이미 서버로 보낸 뒤에는 누구의 기록인지 알 수 없어서 개별 삭제가 어려울 수 있어요.
- 동의하지 않아도 핏체크의 모든 기능을 그대로 쓸 수 있어요.

현재 화면에는 "준비 중이에요. 지금은 서버로 전송되지 않고, 이 브라우저의 대기열에만 저장돼요."가 함께 표시돼요. 실제 전송을 켜기 전에 이 문구와 본 문서를 법무 확인을 거쳐 다시 검토해야 해요.

## 아직 안 한 것

- 서버 저장소, 엔드포인트, 집계, 삭제 처리
- 대기열 전송 코드(동의 후에도 보내지 않음)
- 상품 ID 정규화, k 값 확정, 보관 기간 정책
- 법무 확인
